# Бизнес-процесс и критерии успеха

Документ зафиксирован до реализации (2026-11-11). Критерии ниже проверяются
командами из `REVIEW.md`.

## AS-IS

1. Заявка приходит по почте или в Telegram и попадает в общий список (`leads.json`).
2. Менеджер читает текст, сам определяет тип обращения и срочность.
3. Менеджер пишет ответ с нуля и отправляет его.
4. Руководитель узнаёт о состоянии очереди из устных отчётов.

Проблемы: время уходит на чтение спама и типовых вопросов, срочные заявки
обнаруживаются в порядке очереди, повторные обращения (заявки 1 и 11 в исходном
файле) не связываются между собой, единых правил срочности нет.

## TO-BE

1. Менеджер (или расписание) запускает обработку: `process-leads`, либо в Claude
   Code фразой «обработай новые заявки» или командой `/process-leads`.
2. Агент читает только заявки со статусом `new` через MCP-инструменты, назначает
   категорию и приоритет, готовит короткий черновик ответа на языке клиента и
   записывает результат (`new` → `processed`).
3. Агент формирует сводку руководителю: счётчики, заявки `high` с основанием
   срочности и ближайшим действием, спорные случаи с указанием, что проверить.
4. **Менеджер** остаётся ответственным за результат:
   - первым делом открывает заявки `high` и спорные случаи из сводки;
   - проверяет и редактирует черновик, добавляет подтверждённые факты (тариф,
     срок, статус груза), которых у агента нет;
   - принимает решение об отправке. Агент ничего не отправляет и не выполняет
     внешних действий.

Статус `processed` означает «разобрано агентом, черновик готов», а не «ответ
отправлен».

## Критерии успеха прогона (проверяемые)

| № | Критерий | Как проверяется |
|---|---|---|
| S1 | Каждая исходная заявка `new` учтена | множество ID «найдено» = «записано» ∪ «уже обработано» ∪ «ошибка», множества не пересекаются (`run.json`, поле `reconciliation`) |
| S2 | В штатном прогоне все `new` стали `processed` | независимая сверка файла после прогона: `remaining_new = []` |
| S3 | Исходные данные сохранены | порядок ID, число записей и все поля, кроме `category`, `priority`, `status`, `draft_reply`, совпадают с оригиналом; ранее обработанные записи идентичны (`scripts/compare_leads.py`) |
| S4 | Сводка совпадает с записью | счётчики сводки вычисляются из файла и подтверждённых результатов инструментов; отчёт модели сверяется с файлом по ID (`report_mismatches = []`) |
| S5 | Черновики опираются на факты обращения | автоматические проверки (язык, отсутствие цен, сроков и обещаний без подтверждения) и ручная сверка каждого черновика с текстом заявки по ID |
| S6 | Повторный прогон безопасен | ноль новых заявок, контрольная сумма файла не меняется |

## Показатели пилота

Измерено в прогоне (см. `REVIEW.md`): число обработанных заявок, длительность,
вызовы инструментов, ошибки, токены и сообщённая стоимость, результаты набора
для оценки, сверка по ID.

Требуют базовой линии (до пилота измерить 1–2 недели ручной работы):

| Показатель | Определение | Базовая линия |
|---|---|---|
| Доля черновиков, принятых без правок | отправлено без изменений / все отправленные ответы | нет, собирается в пилоте: менеджер отмечает «принят / исправлен / отклонён» |
| Доля существенных правок | изменены факты или смысл / все черновики | нет |
| Пропуски срочных заявок | заявки, которые менеджер счёл срочными, а агент не отметил `high` | нужна разметка менеджера на выборке |
| Ложные `high` | заявки `high`, которые менеджер понизил | нужна разметка менеджера |
| Время менеджера на заявку | от открытия заявки до отправки ответа | замер хронометражем до и после |
| Время до первого ответа клиенту | от поступления до отправки | из CRM или почты до и после |
| Точность категорий | совпадение с итоговой категорией менеджера | нужна разметка менеджера |

Пороговые значения для решения о масштабировании (предложение): пропуски срочных
— 0 на выборке не менее 200 заявок, принятые без существенных правок — не менее
70 %, время менеджера на заявку — снижение не менее чем на 30 %.
