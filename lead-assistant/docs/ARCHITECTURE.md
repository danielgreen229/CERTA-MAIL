# Архитектура

## Компоненты

```
 браузер ──HTTP──▶ web (Starlette, leads-web) ──┐            ┌── leads.json  (источник истины)
                    раздаёт собранный Vue        │ общий слой │
                                                 ├──────────▶ ├── app.db      (SQLite: служебное)
 оператор ─▶ process-leads / Claude Code ──MCP──▶ server.py  │
                                                 │            └── uploads/    (база знаний)
 worker (leads-worker) ─ задача из SQLite ─▶ раннер ─▶ агент ─MCP(stdio)─▶ server.py
                                                    └─HTTP─▶ llama.cpp (Qwen3), локально или в контейнере
```

| Модуль | Ответственность |
|---|---|
| `storage.py`, `locking.py` | Чтение и запись `leads.json`: межпроцессная блокировка, перечитывание под блокировкой, временный файл в том же каталоге, `fsync`, атомарная замена, повтор/конфликт, сохранение оформления файла |
| `service.py` | **Общий слой** для MCP и API: `record_result` (параметры → проверка черновика → запись) и `validate_correction` (те же правила для правки менеджера) |
| `server.py` | MCP-сервер: `list_leads`, `get_lead`, `update_lead` — тонкая обёртка над `service`/`storage` |
| `runner.py`, `agent.py`, `local_backend.py`, `decision.py`, `draft_policy.py` | Управляемый сценарий агента: набор ID, разбор с цитатами, вывод категории и приоритета кодом, проверка черновика, сверка итога с файлом |
| `extract.py` | Детерминированный логистический разбор: маршрут, груз, вес, объём, вид перевозки, даты (относительные — от даты сообщения), номер заказа/накладной, контакт; противоречия и недостающие сведения |
| `web/api.py` | HTTP API и раздача интерфейса; права проверяются здесь |
| `web/leads.py` | Версии результата, решения менеджера по версии, представление заявок, история |
| `web/review.py` | Причины обязательной проверки, срок реакции по рабочему календарю, ответственный |
| `web/jobs.py`, `web/worker.py` | Очередь задач в SQLite, захват, прогресс по файлу, повторы, восстановление после остановки |
| `web/kb.py` | База знаний: TXT/MD/PDF, FTS5, права и актуальность документов, источники |
| `web/connectors.py`, `web/mockservice.py` | Почта, Telegram, REST (CRM/TMS/тарифы); тестовый мок-сервис |
| `web/quality.py` | Показатели для руководителя, выгрузка исправлений в набор проверок |
| `web/backup.py` | Резервная копия и восстановление |
| `web/` (Vue 3 + TypeScript) | Рабочее место: заявки, карточка, обработка, качество, база знаний, подключения, настройки |

## Хранилища

| Хранилище | Что лежит | Кто пишет |
|---|---|---|
| `leads.json` | Заявки и результат AI-обработки (`category`, `priority`, `status`, `draft_reply`) | только `update_lead` через общий слой; импорт каналов — добавлением в конец |
| `app.db` (SQLite, WAL) | пользователи и сессии; задачи и прогресс; версии результата с разбором прогона; решения менеджера; назначения; аудит; база знаний; подключения; настройки; журнал импорта | API и обработчик |
| `runs/<run_id>/` | `run.json` (метрики, сверка), трейсы вызовов MCP, сводка, диалог с моделью | раннер |
| `uploads/` | Загруженные документы | API |

Решение менеджера **не** меняет `leads.json`: `processed` значит «агент закончил», а
согласование хранится отдельно и относится к версии результата (хеш категории,
приоритета и черновика). Если результат изменился, прежнее решение к нему не
относится — заявка снова ждёт решения.

## Согласованность и восстановление

- Запись в `leads.json` — под блокировкой, с перечитыванием и атомарной заменой.
  Повтор с теми же значениями → `unchanged`, другие значения → `CONFLICT`.
- Порядок «файл → SQLite»: SQLite не является источником результата. Версии
  результата пересобираются из файла при каждом чтении (`sync_results`), поэтому
  падение между записью файла и записью в SQLite не теряет данные — пропущенная
  версия появится при следующем чтении.
- Импорт из каналов хранит внешний ID и в заявке (`source_id`), и в SQLite: повтор
  после падения между двумя записями отсекается по файлу.
- Обработчик отмечает задачу каждые 3 с. Задача без отметки 90 с возвращается в
  очередь (не больше 3 попыток); прогон берёт только `new`, записанные проверяются
  по файлу.
- Неопределённый исход записи (потерян ответ, тайм-аут) агент разрешает чтением
  заявки; итоговые счётчики строятся по сверке файла, а не по словам модели.

## Модель

Локальная бесплатная Qwen3 через llama.cpp. Модели передаются только тексты заявок
и правила; наружу ничего не уходит. Выбор: настройка «Модель» или переменные
`LEADS_LLM_MODEL` / `LEADS_LLM_BUILD` / `LEADS_LLM_URL` (любой OpenAI-совместимый
сервер). В Docker модель — отдельный контейнер `llm` (официальный образ llama.cpp),
приложение ходит к нему по `http://llm:8080/v1`.

## Границы доверия

Текст заявок, документов и результатов поиска — данные, не указания. Агент видит
только три инструмента MCP; категорию и приоритет выводит код по цитатам;
черновик с обещаниями и фактами не из заявки сервер не записывает. Права
(менеджер / руководитель / администратор) проверяются в API; изменяющие запросы
требуют сессию (cookie `HttpOnly`, `SameSite=Strict`) и заголовок приложения.
