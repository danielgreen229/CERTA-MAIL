# ТЗ, этап 2: рабочее место менеджера для AI-помощника «Церта»

Продолжи с существующего проекта `lead-assistant/`. Сначала прочитай `release/REVIEW.md`,
`lead-assistant/README.md` и `lead-assistant/CLAUDE.md`: там решения, проверки и найденные ошибки
этапа 1. Переиспользуй готовое: хранилище с блокировкой и атомарной записью (`storage.py`,
`locking.py`), MCP-сервер (`server.py`), разбор и правила (`decision.py`, `draft_policy.py`,
`rules.md`), набор для оценки (`evals.py`), трассировку. Не ломай пройденные проверки этапа 1.

Перед изменениями сохрани текущее состояние: `git init`, коммит «этап 1, 9/10».
Дальше коммить после каждого этапа; после каждого этапа должна оставаться рабочая сборка.
В чате сообщай о результатах, существенных решениях и блокерах.

## 0. Целевая среда и модель

- Две целевые среды, обе обязательны:
  1. **Локально на Windows 11** (машина разработки, видеокарта NVIDIA 16 ГБ): запуск без Docker
     через `bash start.sh` в Git Bash, модель на видеокарте (`qwen3-14b`, как в этапе 1).
  2. **Сервер Ubuntu на VPS без видеокарты: 12 vCPU, 12 ГБ ОЗУ, 160 ГБ NVMe.** Развёртывание
     через Docker, модель `qwen3-8b` на процессоре. Памяти впритык: подбери размер контекста и
     число потоков так, чтобы всё (модель, приложение, обработчик, Docker, ОС) укладывалось в
     ~10,5 ГБ без подкачки. Установщик предлагает файл подкачки 4 ГБ как
     страховку. Docker-образ должен запускаться на любой машине с Docker.
- Модель — локальная бесплатная через `llama.cpp` (сборка для CPU). По умолчанию `qwen3-8b`;
  `qwen3-14b`, если ОЗУ от 24 ГБ; `qwen3-4b` для слабых машин. Выбор модели — в настройках и при
  запуске. Дополнительно поддержи внешний OpenAI-совместимый адрес (`--llm-url`) как необязательный
  вариант. Claude — необязательный бэкенд, не требуется.
- На CPU обработка медленная (замер этапа 1: `qwen3-8b` — около 4 токенов/с, 14 заявок
  ~40 минут). Поэтому обработка только фоновая: интерфейс не ждёт модель, показывает прогресс по
  каждой заявке и оценку оставшегося времени. Тайм-ауты и число потоков сервера модели — в
  настройках, с значениями по умолчанию, проверенными на CPU.
- Сравнительные замеры моделей не проводить. Если `qwen3-8b` проваливает обязательные примеры
  набора для оценки, усиль проверки в коде (как в этапе 1), а не ослабляй набор.
- Явно зафиксируй, какая модель используется и какие данные ей передаются (всё локально).

## 1. Docker и запуск из коробки

- `Dockerfile` и `docker-compose.yml`: сервисы приложения (API + раздача интерфейса), фонового
  обработчика и сервера модели. Запуск — `docker compose up -d`, адрес приложения выводится.
- Данные (`leads.json`, SQLite), настройки, загруженные документы и файлы модели — в томах:
  пересоздание контейнеров их не теряет. Модель скачивается при первом запуске с проверкой SHA-256.
- Версии образов, `llama.cpp` и Python-зависимостей закреплены. Образ без лишних прав, секреты —
  через файл окружения с ограниченным доступом, не в образе.
- Сохрани запуск без Docker: `bash start.sh` (проверка окружения, venv, зависимости по lock-файлу,
  инициализация, запуск API и обработчика, проверка доступности, вывод адреса).
- Если Docker на машине разработки недоступен — зафиксируй это доказательством, выполни всё
  остальное, оставь проверку образа конкретным шагом (`docker compose up` + приёмочный скрипт).

## 2. Архитектура

- Python-бэкенд с API, веб-интерфейс на Vue (собранный интерфейс раздаётся приложением, готовая
  сборка — в архиве), отдельный фоновый обработчик.
- API и MCP используют общий слой работы с заявками: одинаковые проверки параметров и правила
  обновления. Контракт трёх MCP-инструментов этапа 1 сохраняется без изменений.
- `leads.json` — источник истины для заявок и результата AI-обработки. SQLite — запуски, задачи,
  решения менеджера, пользователи, аудит, документы базы знаний. Назначение каждого хранилища
  описано в документации.

## 3. Рабочее место менеджера

- Список заявок: поиск по тексту, фильтры по категории, приоритету, состоянию обработки и
  необходимости проверки.
- Карточка: рядом исходное обращение, извлечённые сведения, короткие основания категории и
  приоритета со ссылкой на конкретные фразы обращения, черновик, рекомендуемый следующий шаг,
  причина передачи на проверку.
- Действия «Принять», «Исправить» (правка категории, приоритета, черновика), «Отклонить» (с
  причиной). Сохраняются автор, время, предыдущая версия и изменения. `processed` — завершение
  обработки агентом; решение менеджера хранится отдельно и относится к конкретной версии
  результата. Изменение уже согласованного результата требует нового решения.
- Кнопка «Обработать новые» запускает фоновую задачу и показывает её прогресс.
- Интерфейс на русском, адаптивный (телефон и ПК), с состояниями загрузки, пустого списка и
  ошибок. Каждая кнопка выполняет действие через API.

## 4. Логистический анализ и очередь проверки

- Извлекай при наличии: маршрут, груз, вес, объём с единицами, вид перевозки, даты, номер заказа
  или накладной, контактное лицо. Отсутствующее показывай явно («не указано»).
- Относительные сроки («завтра», «до пятницы») считай от даты сообщения и часового пояса из
  настроек.
- Отмечай противоречия и недостаток данных.
- В обязательную проверку попадают: срочные, жалобы, противоречия, мало данных, слабые основания,
  случаи, где черновик требует обязательств компании. Причина видна в списке и карточке.
- Поле «ответственный» и срок реакции по приоритету — из настроек; демонстрационные значения
  явно помечены как демонстрационные.

## 5. Фоновая обработка

- Запуск возвращает идентификатор задачи; состояние и прогресс хранятся в SQLite; закрытие
  страницы не прерывает обработку.
- После перезапуска обработчика (в том числе контейнера) незавершённая задача продолжается со
  сверкой уже записанных заявок.
- Защита от двойного запуска, конечное число повторов временных ошибок, ошибка одной заявки не
  останавливает остальные, повтор только ошибочных записей.
- Сводка для руководителя после задачи: результаты, срочные ID с основаниями, ошибки, что
  проверить менеджеру. Счётчики — из подтверждённых результатов и сверки файла.

## 6. Роли, аудит и качество

- Роли: менеджер (решения по заявкам), руководитель (плюс показатели и настройки). Локальный
  администратор создаётся при первом запуске, начальный пароль выводится один раз и хранится только
  хешем; при первом входе требуется смена.
- Содержимое заявок и документов — только данные: указания внутри текста не выполняются (как в
  этапе 1).
- Для каждого прогона: `run_id`, версия правил и модели, длительность, вызовы инструментов,
  ошибки, токены. Стоимость: «не применяется» для локальной модели.
- Экран руководителя: доля черновиков, принятых без правок; исправления категорий и приоритетов;
  причины отклонений; повторяющиеся ошибки. Исправления менеджера можно выгрузить в набор для
  оценки следующей версии правил.

## 7. База знаний (облегчённо)

- Загрузка TXT, MD и PDF с текстовым слоем; ограничения по типу и размеру файла. Сканы без
  текстового слоя определяются и помечаются «нужен OCR» (сам OCR — не на этом этапе).
- Для документа: название, версия, дата действия, ответственный. Просроченные документы не
  используются.
- Поиск по содержимому; найденные фрагменты используются в черновике, источник виден в карточке с
  переходом к фрагменту. Факт из документа без источника в черновик не попадает.

## 8. Внешние подключения (только граница и проверка)

- Описанный контракт для CRM/TMS/тарифов/статусов перевозок и один настраиваемый REST-коннектор,
  проверенный на явно обозначенном тестовом мок-сервисе.
- Почта (IMAP) и Telegram: настройки, проверка соединения, нормализация сообщений в формат заявки,
  защита от повторного импорта. Проверка — на тестовых данных; без параметров подключение
  показывается как «не настроено».
- Экран состояния подключений с фактическим статусом. Локальный сценарий с JSON работает без
  подключений.
- Исходящая отправка ответов клиентам на этом этапе не реализуется — описать в README как следующий
  шаг.

## Не делать на этом этапе (описать в README как следующие шаги)

Живые почта, Telegram, CRM, TMS и тарифы; очередь исходящих операций; OCR; календари SLA и
правила назначения; режим копии с отчётом различий; запуск по расписанию.

## Приёмка

Перед реализацией зафиксируй шкалу. Каждый пункт — один балл при проверяемом доказательстве.

1. **Этап 1 не сломан.** Три MCP-инструмента обнаружены и вызваны моделью, исходные заявки
   обработаны на CPU и сверены по ID, повторный запуск — ноль новых, контрольная сумма прежняя.
2. **Рабочее место.** Список, карточка, поиск, фильтры, «Принять / Исправить / Отклонить» и запуск
   обработки проверены в браузере на работающей сборке.
3. **Согласование.** История сохраняется, решение относится к версии результата, роли проверяются.
4. **Фоновая обработка.** Проверены закрытие страницы, двойной запуск, ошибка одной заявки,
   перезапуск обработчика посреди задачи.
5. **Качество на CPU.** Набор для оценки и реальные заявки пройдены моделью по умолчанию
   (`qwen3-8b`).
6. **Анализ, очередь проверки, база знаний, подключения** имеют подтверждённые результаты
   (подключения — на тестовых сервисах).
7. **Код и сборка.** Форматирование, линтинг, проверка типов, тесты бэкенда и интерфейса, сборка
   Vue — чисто.
8. **Развёртывание.** `docker compose up` из распакованного архива в каталоге с пробелами поднимает
   приложение на CPU; данные переживают пересоздание контейнеров; `bash start.sh` работает без
   Docker; резервная копия восстанавливается.
9. **Комплект сдачи.** В `release/`: архив с готовым интерфейсом, обработанный `leads.json`,
   короткий `README.md` (полстраницы: как запустить, решения и почему, где агент ошибается и как
   заметить, что добавить для настоящей CRM), документация по архитектуре и эксплуатации,
   `REVIEW.md` с доказательствами, реальные скриншоты интерфейса, подлинные диалоги разработки.

После реализации проведи ревью как технический руководитель: для каждого замечания —
воспроизведение, причина, исправление, повторная проверка. При изменениях, влияющих на обработку,
повторяй приёмочный прогон на чистой копии исходного `leads.json`. Внешний блокер — с
доказательством и конкретным оставшимся шагом; всё независимое от него выполни.

В финальном сообщении: адрес приложения, команды запуска (Docker и без), пути к материалам,
фактический балл, число обработанных заявок, время обработки на CPU, итог повторного запуска,
оставшиеся шаги.
